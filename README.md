# Задание 3. Библиотека метрик

Дедлайн – 29 ноября, 23:59 по Москве. 10 баллов.

## 1. Задача

Сервис считает запросы, хранит текущую длину очереди и записывает время ответа. Метрики обновляют потоки сервиса, а Prometheus периодически забирает их одним запросом. Напишите библиотеку, которая собирает эти данные и выдаёт их в текстовом формате Prometheus.

## 2. Контракт

### 2.1. Типы

Все классы находятся в пакете `edu.hse.concurrency.metrics`.

| Тип | Что это |
|---|---|
| `MetricId` | имя метрики и теги; проверяет имя, ключи тегов, `__`, `le` и `null` |
| `MetricType` | `COUNTER`, `GAUGE`, `TIMER` |
| `Counter` | `increment()`, `count()` |
| `Gauge` | `set(long)`, `get()` |
| `Timer` | `record(long)`, `snapshot()` |
| `TimerSnapshot` | `count`, `totalNanos`, `maxNanos`, `cumulativeBuckets` |
| `Registration` | подписка; `close()` |
| `RegistrationListener` | обработчик новой метрики |
| `MetricsRegistry` | интерфейс реестра |
| `MetricsRegistryImpl` | реализация |

Сигнатуры выданных типов и тесты менять нельзя. Свои классы добавлять можно. У `MetricsRegistryImpl` должен остаться публичный конструктор без аргументов: его использует `CounterBenchmark`.

`MetricId` проверяет имя и ключи тегов, но не знает тип метрики. Кроме того, реестр проверяет окончание имени по типу метрики и границы таймера.

### 2.2. Реестр

| Метод | Результат |
|---|---|
| `counter(name, tags)` | Счётчик запросов или других событий |
| `gauge(name, tags)` | Текущее значение, например длина очереди |
| `timer(name, tags, upperBoundsNanos…)` | Таймер с гистограммой задержек |

Ключ метрики – имя и набор пар тег → значение. Порядок тегов не важен. Для одного ключа повторный вызов возвращает тот же объект, в том числе при одновременной регистрации. У одного имени один тип для всех наборов тегов; у таймера с одним именем одни и те же границы бакетов. Вызов с другим типом или границами бросает `IllegalArgumentException` и оставляет реестр в прежнем состоянии.

Реестр сохраняет копии тегов и массива границ. Изменение исходных данных после вызова не меняет уже зарегистрированную метрику.

### 2.3. Запись и чтение

| Метод | Поведение |
|---|---|
| `Counter.increment()` | Прибавляет 1. Начальное значение – 0 |
| `Counter.count()` | Возвращает число событий. После завершения всех записей значение точное |
| `Gauge.set(value)` | Устанавливает значение `long`. Допустимы и отрицательные значения |
| `Gauge.get()` | Читает текущее значение. Начальное значение – 0 |
| `Timer.record(nanos)` | Добавляет измерение в наносекундах. Ноль допустим |
| `Timer.snapshot()` | Снимает число измерений, сумму, максимум и накопительные счётчики бакетов |

Бакеты накопительные: бакет с границей `B` содержит все измерения, не превышающие `B`. Измерение ровно на границе попадает и в этот бакет, и во все бакеты с большими границами. Бакет `+Inf` содержит все измерения. В `TimerSnapshot.cumulativeBuckets` столько элементов, сколько границ, плюс один для `+Inf`. До первой записи число измерений, сумма, максимум и значения бакетов равны нулю.

Все поля одного `TimerSnapshot` относятся к одному состоянию таймера, поэтому `+Inf` всегда равен `count`. Пара `count = 7` при `+Inf = 8` означает, что снимок собран из разных состояний; это ошибка. После получения снимок не меняется.

Переполнение `long` проверять не нужно, в том числе при суммировании.

### 2.4. Выгрузка

`scrape()` возвращает строку в текстовом формате Prometheus 0.0.4. Для каждого имени выведите одну строку `# TYPE` с типом `counter`, `gauge` или `histogram`, затем все серии этого имени без временных меток. Других строк, в том числе `# HELP`, быть не должно. Порядок имён, серий и тегов произвольный. Бакеты одной серии идут по возрастанию границ, `+Inf` – последним. Строка заканчивается переводом строки `\n`, пустой реестр возвращает пустую строку. [Формат выгрузки Prometheus](https://prometheus.io/docs/instrumenting/exposition_formats/#text-format-details)

Пример вывода для `request_seconds` с границей 1 000 000 нс и одной записью в 500 000 нс.

```text
# TYPE request_seconds histogram
request_seconds_bucket{route="/orders",le="0.001"} 1
request_seconds_bucket{route="/orders",le="+Inf"} 1
request_seconds_count{route="/orders"} 1
request_seconds_sum{route="/orders"} 0.0005
```

Границы и сумму выводите в секундах десятичной записью без экспоненты. Максимум в `scrape()` не выводится, он доступен через `snapshot()`. У счётчиков и gauge имя в строке данных совпадает с именем метрики. У `_bucket` тег `le` есть всегда, даже если других тегов нет. Остальные `{}` опускаются, когда тегов нет. В значениях тегов экранируйте обратную косую черту, кавычку и перевод строки как `\\`, `\"` и `\n`.

Зарегистрированная, но ещё не обновлявшаяся метрика выводится с нулями.

Можно вызывать `scrape()` одновременно с регистрацией и записью. Для каждого таймера берите один согласованный снимок, в котором `+Inf` равен `_count`. Разные серии разрешено читать в разные моменты.

### 2.5. Подписчики

`onRegistration(listener)` подписывает на появление новых метрик и возвращает `Registration`. Вызов `close()` снимает эту подписку. Повторный `close()` ничего не делает.

О создании ключа сообщает только поток, который впервые его зарегистрировал. Он делает метрику видимой другим потокам, затем берёт текущий список подписок и вызывает каждый обработчик один раз, синхронно, до возврата из своего метода. Повторный запрос того же ключа и сама подписка уведомлений не вызывают. Снятие подписки не отзывает уведомление, если оно уже попало в список на отправку.

Вызывайте обработчики вне блокировок реестра. Подписчик может обратиться к реестру из обработчика. `RuntimeException` одного подписчика реестр перехватывает: остальные обработчики вызываются, регистрация сохраняется, наружу исключение не пробрасывается.

### 2.6. Требования

1. Методы реестра, метрик и `scrape()` можно вызывать из любого числа потоков одновременно.
2. Один ключ – один объект. У имени один тип, у таймера с одним именем одни границы.
3. Счётчик не теряет обновлений. `Gauge.get()` возвращает последнее записанное значение.
4. Снимок таймера согласован: все поля относятся к одному состоянию, `+Inf` равен `count`.
5. `scrape()` работает при одновременной регистрации, записи и чтении.
6. Подписка получает только новые ключи, `close()` идемпотентен, вызов реестра из обработчика не блокируется и не зацикливается.
7. Программа не зависает и не бросает исключений, которых нет в контракте.

## 3. Ограничения

### 3.1. Входные данные

| Что | Допустимо | Иначе |
|---|---|---|
| имя метрики, ключ тега | `[a-zA-Z_][a-zA-Z0-9_]*` | `IllegalArgumentException` |
| имя счётчика | заканчивается на `_total` | `IllegalArgumentException` |
| имя таймера | заканчивается на `_seconds` | `IllegalArgumentException` |
| имя gauge | без окончаний `_total`, `_seconds`, `_bucket`, `_count`, `_sum` | `IllegalArgumentException` |
| ключ тега | без префикса `__`; `le` зарезервирован | `IllegalArgumentException` |
| границы таймера | от 1 до 20 значений `long`, неотрицательные, строго возрастают | `IllegalArgumentException` |
| измерение таймера | `nanos ≥ 0` | `IllegalArgumentException` |
| любой аргумент, ключ и значение тега | не `null` | `NullPointerException` |
| значение тега | любая строка | допустимо |

Сначала проверяются аргументы. Некорректный вызов не меняет состояние реестра.

### 3.2. Средства

Разрешено:

- атомарные классы `java.util.concurrent.atomic`, `VarHandle`;
- для реестра и подписок – конкурентные коллекции, `synchronized`, локи JDK;
- в тестах и замерах – всё, включая сторонние библиотеки.

Запрещено:

- в `increment`, `count`, `set`, `get`, `record` и `snapshot` – `synchronized`, локи, `wait`/`notify`, `LockSupport.park`, `sleep`, `yield`, `onSpinWait`, цикл опроса;
- в них же – ожидание в цикле, пока другой поток не закончит запись;
- сторонние библиотеки в `main`.

Повтор из-за неудачного CAS разрешён: он не ждёт конкретный поток.

## 4. Замер

В `CounterBenchmark` уже есть счётчики на `synchronized` и `AtomicLong`. Третий вариант использует ваш `Counter`. Каждый прогон измеряет обновления одного счётчика, общего для всех рабочих потоков.

```bash
./gradlew jmh -PjmhThreads=1
./gradlew jmh -PjmhThreads=4
./gradlew jmh -PjmhThreads=16
```

Запишите `Score ± Error` в `ops/s`, процессор, число ядер и версию JDK. Объясните, как число потоков повлияло на каждый вариант.
